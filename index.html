Bloc 1 · TD 1→4

Le Datawarehouse

ETL · DataPull/Push · DataMart · Architecture décisionnelle

4 propriétés fondamentales

Un entrepôt de données centralisé pour l'aide à la décision, pas les transactions.

Orienté sujet

Organisé par thème métier (blessures, matchs...), pas par application.

Intégré

Toutes les sources fusionnées en un format commun.

Historisé

Données passées conservées avec horodatage. Analyse dans le temps.

Non-volatile

Données jamais modifiées ni supprimées. Garantie de fiabilité.

Architecture à 3 niveaux

1. Sources hétérogènes → Excel, Access, logiciels séparés
2. ETL → Extraction · Transformation · Chargement
3. DWH → Datawarehouse central
4. DataMarts → sous-ensembles spécialisés
5. Décision → KPI · Tableaux de bord · Stratégie

💡 Analogie : le DWH = bibliothèque nationale. Tout est centralisé et archivé. Les bases opérationnelles = guichets d'accueil, actifs mais temporaires.

ETL = Extract → Transform → Load

E — Extract (Extraire)

Se connecter à chaque source et récupérer les données brutes.

DataPull : le DWH va chercher les données (ex : interroge Access toutes les nuits). Le système central contrôle le rythme.

DataPush : les sources envoient les données (ex : 16 clubs envoient leur CSV chaque lundi). Les sources initient.

T — Transform (Transformer)

L'étape la plus critique (70% du travail) :

  • Uniformiser formats (01/01/2025 ≠ 2025-01-01 → format unique)
  • Supprimer les doublons
  • Gérer les valeurs manquantes
  • Traduire les codes (ID 42 → "Raja Casablanca")

L — Load (Charger)

Full load : tout recharger (simple, lent)
Incremental load : seulement les nouvelles données (rapide, recommandé)

✅ Moyen mémo : cuisiner. Courses dans plusieurs épiceries (Extract) → préparer les ingrédients (Transform) → remplir le frigo central (Load).

DataMart — sous-ensemble spécialisé

Portion du DWH dédiée à un département. Si le DWH est une bibliothèque nationale, le DataMart = la section "Sciences du Sport".

Pourquoi ?

  • Performance : requêtes sur moins de données
  • Sécurité : le médecin voit seulement les données médicales
  • Simplicité : chaque département n'a que ce dont il a besoin
  • Indépendance : panne d'un DataMart ≠ panne du DWH

Médical

Blessures, récupération, antécédents par poste

Performance

Buts, passes, distance, évolution saisonnière

Financier

Salaires, coût joueurs, revenus billetterie

Formation

Résultats académiques, présences, progression

⚠️ Sans DWH central, seulement des DataMarts → chaque département définit les KPI différemment → incohérences. Le DWH garantit une "version unique de la vérité".

Pour comparer les 2 dernières années, il faut garder les données passées. La BD opérationnelle écrase les anciennes valeurs ; le DWH les conserve toutes avec horodatage.

Q2 — ETL dans ce cas
Extract : récupérer les 4 sources → Transform : uniformiser ID joueurs, vérifier dates, supprimer doublons → Load : DWH central

Q3 — Deux DataMarts
DataMart Santé (blessures, durée récupération, taux par club) et DataMart Performance (stats matchs, évolution saisonnière)

Q4 — Comment le DWH améliore la décision ?
Permet de croiser données médicales + performance → identifier clubs à fort taux de blessures, analyser impact budget, suivre l'évolution nationale.

Q1 — Étapes du processus décisionnel
1. Identifier le problème · 2. Collecter les données (via DWH) · 3. Analyser (croiser sources) · 4. Générer des hypothèses · 5. Décider · 6. Évaluer

Q2 — Rôle du DWH
Centralise stats + médical + entraînement → base factuelle pour décider : changer entraîneur ? Modifier programme ? Recruter ?

Q3 — Mauvaise décision sans données intégrées ?
Si on ignore les données médicales, on risque de modifier le programme d'entraînement alors que la vraie cause est une vague de blessures.

Schéma en étoile

1 table de faits au centre (mesures) + N tables de dimensions autour (contexte).

Table de Faits — Faits_Performance

Clés étrangères (FK) : ID_Joueur · ID_Temps · ID_Comp · ID_Club

Mesures : Buts · Passes · Distance · Score · Durée_Blessure

Chaque ligne = 1 événement. Ex : Ahmed, match M01, 3 buts, 2025-01-15.

Dim_Temps

Quand ? Jour, Mois, Année, Saison, Trimestre

Dim_Joueur

Qui ? Nom, Poste, Âge, Nationalité, Nom_Club

Dim_Compétition

Contexte ? Nom, Niveau, Type, Pays

Dim_Club

Où ? Nom_Club, Région, Budget, Ville

⚠️ Pourquoi dénormaliser ? En 3NF, l'analyse "buts par joueur par saison" nécessite 15 JOIN. En étoile : seulement 4 JOIN → beaucoup plus rapide. La redondance est acceptée volontairement.

SQL & OLAP

SELECT · JOIN · GROUP BY · SUM · COUNT · AVG

Requête OLAP annotée

SELECT j.Nom, -- dimension 1 : qui t.Saison, -- dimension 2 : quand SUM(f.Buts) AS Total_Buts -- mesure FROM Faits_Performance f -- table de faits JOIN Dim_Joueur j ON f.ID_Joueur = j.ID_Joueur JOIN Dim_Temps t ON f.ID_Temps = t.ID_Temps GROUP BY j.Nom, t.Saison;

SELECT

Colonnes à afficher : dimensions + mesure agrégée

FROM

Toujours la table de faits avec un alias court (f)

JOIN…ON

FK du faits = PK de la dimension. 1 JOIN par dimension.

WHERE

Filtrer AVANT groupement. Ex: t.Saison='2024'

GROUP BY

Mêmes colonnes que SELECT (sans la mesure agrégée)

HAVING

Filtrer APRÈS groupement. Ex: SUM(f.Buts)>10

✅ Règle d'or : tout ce qui est dans SELECT (hors fonctions agrégées) doit être dans GROUP BY. Oublier → erreur SQL.

SUM(f.Buts) → total des valeurs
COUNT(*) → nombre de lignes
AVG(f.Score) → moyenne
MAX/MIN(f.Buts) → extrêmes

TD 10 + Mini-Projet — Corrigés

SELECT Nom, Poste FROM Joueur;

Colonnes affichées : Nom et Poste

Table source : Joueur (table opérationnelle)

Nb lignes : tous les joueurs (pas de WHERE)

Consigne : afficher nom des joueurs et leur nombre total de buts.

SELECT j.Nom, SUM(s.Buts) AS Total_Buts FROM Joueur j JOIN Statistiques s ON j.ID_Joueur = s.ID_Joueur GROUP BY j.Nom;

Sans GROUP BY, SQL ne sait pas comment agréger SUM par joueur → erreur.

SELECT j.Nom, SUM(s.Buts) FROM Statistiques s JOIN Joueur j ON ____________ GROUP BY ____________;

ON s.ID_Joueur = j.ID_Joueur — FK de Statistiques = PK de Joueur

GROUP BY j.Nom — même colonne non-agrégée que dans SELECT

SELECT t.Saison, SUM(f.Buts) FROM Faits_Performance f JOIN Dim_Temps t ON f.ID_Temps = t.ID_Temps GROUP BY t.Saison;

Cette requête calcule le total de buts par saison → analyse OLAP typique. 1 ligne par saison avec son total.

1. Par joueur :

SELECT j.Nom, SUM(f.Buts) AS Total_Buts FROM Faits_Performance f JOIN Dim_Joueur j ON f.ID_Joueur = j.ID_Joueur GROUP BY j.Nom;

2. Par saison :

SELECT t.Saison, SUM(f.Buts) AS Total_Buts FROM Faits_Performance f JOIN Dim_Temps t ON f.ID_Temps = t.ID_Temps GROUP BY t.Saison;

3. Par joueur ET par saison (2 dimensions) :

SELECT j.Nom, t.Saison, SUM(f.Buts) AS Total_Buts FROM Faits_Performance f JOIN Dim_Joueur j ON f.ID_Joueur = j.ID_Joueur JOIN Dim_Temps t ON f.ID_Temps = t.ID_Temps GROUP BY j.Nom, t.Saison;

4. Par compétition :

SELECT c.Nom_Compétition, SUM(f.Buts) AS Total_Buts FROM Faits_Performance f JOIN Dim_Compétition c ON f.ID_Comp = c.ID_Comp GROUP BY c.Nom_Compétition;

Lire les coefficients

Coefficient aᵢ = effet d'1 unité de Xᵢ sur Y, toutes les autres variables constantes.

Ex : coefficient VO2max = +0.42 → augmenter la VO2max de 1 prédit +0.42 points de performance. Coefficient négatif = effet inverse (Stress ↑ → performance ↓).

Modèle complet

Toutes les X1→X10. R² maximal mais risque de surapprentissage.

Modèle réduit

Seulement p<0.05. R² ajusté souvent meilleur. Plus interprétable.

⚠️ R² élevé ≠ bon modèle. Toujours vérifier R² ajusté ET les p-values avant de conclure. Un modèle avec 10 variables peut avoir R²=0.99 mais être inutile.

Indice de Gini

Gini = 1 − Σ p²

p = proportion de chaque classe. Gini=0 → pur (une seule classe). Gini=0.5 → 50/50 (maximal).

Règles d'association — A → B

Support

|A∩B| / N

Fréquence de la règle dans les données

Confiance

Supp(A∩B)/Supp(A)

P(B|A) — si A vrai, prob que B soit vrai

Lift

Confiance(A→B) / Support(B)

Lift >1 = association positive réelle · =1 = indépendance · <1 = association négative

Q2 — Confiance :

Confiance = 0.50 / 0.667 = 0.75
→ quand fatigué, 75% de chance d'avoir une douleur.

Q3 — Lift :
Supp(Douleur) = 3/6 = 0.50
Lift = 0.75 / 0.50 = 1.5 → association positive
→ La fatigue est un facteur de risque réel (+50% vs hasard).

Règle Échauffement incomplet → Blessure :

Données : 7 observations (Échauffement complet, Fatigue élevée, Blessure)

Apriori : Si un ensemble est fréquent, tous ses sous-ensembles le sont aussi. L'algorithme génère automatiquement toutes les règles avec support_min et confiance_min définis.

Étapes : 1. Fixer les seuils · 2. Trouver itemsets fréquents · 3. Générer les règles · 4. Garder celles avec Lift>1

Interprétation : Une règle avec confiance élevée mais support faible → règle rare, peut-être due au hasard. Une règle avec support élevé mais confiance faible → peu fiable. Le Lift normalise les deux.
